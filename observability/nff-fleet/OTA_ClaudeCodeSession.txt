  Root cause: an off-by-one buffer bug in the SDK verifier — not a key/security 
  problem

  nff_security.c declared the signature hex buffer one byte too small:

  char sig_hex[144];   // ECDSA-P256 DER sig can be 72 bytes = 144 hex chars → 
  needs 145 (with NUL)

  When the fleet's signature is 72 bytes — which happens ~26% of the time
  (whenever both r and s get a sign-pad byte; measured 521/2000) — its 144-char
  hex value can't fit, nff_json_get_str returns -1, and the device rejects with
  the misleading cmd rejected (security). The other ~74% (≤71-byte sigs)
  verified fine, which is why it was intermittent and looked random.

  What I ruled out, with evidence:
  - Keys — fleet cmd_sign.pem pubkey, cmd_verify.bin, and the device's embedded
  NFF_CMD_VERIFY_KEY_DER are byte-identical.
  - TBS format — fleet and device both build "{action}|{nonce}|{timestamp}"; the
  on-device capture showed tbs=ping|d000f3a2|1780525615.
  - Crypto — on-device ecdsa_rc=0 for every 71-byte sig → genuine pong, ~600 ms
  RTT.

  The instrumented capture nailed it: every success had sig_len=71; the failures
  are the 72-byte case overflowing the buffer.

  nff-sdk-c/src/nff_security.c: sig_hex[144] → sig_hex[145] (with a comment
  explaining why), in the repo (source of truth). Synced to the Arduino lib and
  reflashed via flash.ps1. Debug instrumentation fully reverted (verified no DBG
  remnants). Result: 14 consecutive ping successes.

  What this means for OTA

  There were two independent buffer bugs blocking OTA, now both fixed:
  1. MQTT RX buffer 256 → 1024 (PubSubClient silently dropped the ~421 B OTA
  command) — the original SDK change.
  2. Signature buffer 144 → 145 (this one) — rejected ~26% of all signed
  commands, OTA included.
